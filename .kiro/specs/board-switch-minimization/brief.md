# Brief: board-switch-minimization

作成日: 2026-10-20
状態: Discovery。ユーザーがB案を選択済み。要件・設計・実装は未着手。

## Problem

通常版WindowBoardの利用者から、Board切替後に未登録ウィンドウが最小化されず残るとの報告がある。切替結果を予測しづらく、作業対象のウィンドウへ切り替える目的が満たされない。
残るアプリ名、発生頻度、切替入口、自動最小化設定の実際の値は未確認。コード上の原因候補は確認したが、今回の報告と特定の分岐の因果関係は実機では確定していない。

## Current State

### 実装で確認した事実

- 通常画面・Status Item・Launcherの切替状態は `WorkspaceSessionController` に集約される。外部ウィンドウ操作は `AccessibilityWindowService` を境界にする。
- 自動最小化は `minimizeUnattachedOnWorkspaceSwitch` が有効な場合に実行される。既定値はfalse。
- 主画面は候補キャッシュを渡す。登録ウィンドウがすべて解決すると再列挙を省略するため、その後に開いたキャッシュ外の未登録ウィンドウを最小化候補へ含めない経路がある。
- Status Itemの通常切替はキャッシュを渡さず列挙する。同じSessionでも入口によって候補の網羅性が異なる。
- 自動最小化はBoard表示後に遅延実行する。別の最小化が実行中なら開始を見送り、最新要求を後から実行する仕組みがない。
- 開始前にrevisionを確認するが、実際の最小化・登録ウィンドウ復元ループには操作ごとのrevision確認がない。開始済みの旧処理は新しい切替後も副作用を起こし得る。
- 手動最小化も `isMinimizingUnattached` と共通の実行処理を使う。自動処理だけを直しても手動操作との競合が残り得る。
- 利用可能な登録Terminalがあると、未登録Terminalも同一アプリ保護で除外される。空Boardでは自動最小化を開始しない。いずれも今回の報告原因と確定していない。
- 自動最小化ONでキャッシュ漏れ・連続切替・入口差を検証する明示テストは、調査範囲では見つからなかった。

### 根拠

- `WindowBoard/Views/ContentView.swift`: `loadWorkspace` のキャッシュ引き渡し。
- `WindowBoard/App/WorkspaceSessionController.swift`: `switchWorkspace`、`minimizeUnattachedAfterWorkspaceSwitch`、`minimizeUnattachedWindows`、`minimizeWindows`、`isAmbiguousSameAppWindow`。
- `WindowBoard/App/WindowBoardStatusItemController.swift`: `loadWorkspace`、手動最小化。
- `WindowBoard/Services/AccessibilityWindowService.swift`: AX列挙、最小化状態の取得・設定。
- `WindowBoardTests/WindowMatchingTests.swift`: キャッシュで列挙を省くLauncher切替、手動最小化、切替revisionの既存テスト。

## Desired Outcome

- 自動最小化ON時、キャッシュに登録ウィンドウがあることを理由に、未登録候補の補完が省略されない。
- Boardの表示は従来どおり先に更新し、候補補完・最小化の終了を待たせない。
- 連続切替や手動最小化との重複でも最新Board向けの要求を失わず、操作が落ち着いた後は最新Boardの登録ウィンドウを保護する状態に揃える。
- 古い切替向け処理は各操作の区切りで失効を検知して停止し、古い完了通知が新しい処理のbusy状態・ステータスを上書きしない。世代確認と同期AX呼出の間に発生する切替は、最新要求による再整合で扱う。
- 対象漏れ、保護による除外、AX失敗、旧処理の中断を診断上区別できる。

## Approach

**採用: B案「最小化の実行管理を整える」**。2026-10-20にユーザーが選択。

- Sessionが最新要求、処理世代、実行状態を所有する。必要なら純粋な計画型や狭い調停処理を抽出するが、第二のセッション状態所有者は作らない。
- 高速なキャッシュ解決と、未登録集合を判断できる候補一覧を区別する。候補の取得範囲・世代を扱い、切替中に取得済みの適切な一覧は再利用する。
- キャッシュだけでは対象集合の網羅性が不明なら、Board表示後に背景列挙で補完する。TTLだけを完全性の根拠にせず、毎回無条件の重複全列挙や切替前の同期列挙へ戻さない。具体的な鮮度条件は設計で定義する。
- 最小化を直列に調停し、処理中の新しい要求は最新要求として保持する。旧処理の終了・中断後に最新の対象と登録保護情報で再計画する。
- AX操作の区切りで世代の有効性を確認する。実行中の同期AX呼出自体は強制中断できないため、完了後に次の操作を止め、最新Boardへの整合処理を行う。
- 最小化成功など実際に生じた副作用の記録と、最新画面への結果適用を区別する。旧世代の結果を一括破棄して復元履歴から実際の操作を失わない方針を設計する。
- 診断は既存の低ノイズDebugログを基本とし、候補数、保護理由、失敗数、中断・再計画を識別する。利用者に技術情報の操作を要求しない。

A案の候補漏れだけの修正は競合を残すため不採用。C案の切替全体再構成は変更範囲が大きいため見送る。

## Scope

- **In**: 通常版の切替時自動最小化、候補補完、最新要求の保持、実行世代管理、手動最小化との競合、関連する登録ウィンドウの復元と結果記録、回帰テスト・診断。
- **Out**: Tree版、分割UI試作、本番UIの置換、保存形式移行、平坦グループ導入、配置保存の意味変更、Followや前面化全体の再設計、新規ライブラリ導入。

## Boundary Candidates

- **Session / Workspace**: 切替対象、登録集合、所有Board、最新要求、完了結果の適用。Session本体の主変更者は一人にする。
- **AX / Window Operations**: AX境界、候補取得、操作の実行・失敗・中断可能な区切り。セッション状態や永続化は所有しない。
- **Performance / Regression**: キャッシュ経路の維持、候補の補完回数、操作順序、連続切替、入口差の検証。
- UIは既存の入口・表示を維持し、必要な要求・結果の受渡しに限定する。現時点では単一仕様内の責務分担であり、別仕様へ分割しない。

## Out of Boundary

- 自動最小化設定の既定値や既存ラベルを変更しない。
- Terminalの広い同一アプリ保護を一括削除しない。識別可能な別ウィンドウだけ保護を限定するかは、アプリ名・再現情報と誤最小化リスクを確認して決める。
- 空Boardへ切り替えた際に全ウィンドウを最小化するかは別の仕様判断とし、今回暗黙に変更しない。
- 同一構成内での選択変更を、外部操作を伴うBoard切替へ自動的に変更しない。
- 別Space・フルスクリーン・システムウィンドウへの制御保証は追加しない。

## Upstream / Downstream

- **Upstream**: 現行WorkspaceSessionController、BoardCompositionStoreの合成結果、WorkspaceWindowOperating、AXサービス、候補キャッシュ、既存の自動最小化設定。
- **Downstream**: 主画面・Status Item・Launcherの切替結果、手動復元履歴、将来のBoard切替改善。次期平坦グループの導入に依存させない。

## Existing Spec Touchpoints

- **Extends**: 対応する既存 `.kiro/specs/*/spec.json` は調査時点では存在しない。新規単一仕様候補（Path C）。
- **Adjacent**: `AGENTS.md`、`.kiro/steering/`、`APP_REQUIREMENTS.md`、`BASIC_DESIGN.md`。次期設計を現行本番実装と混同しない。
- 既存文書の挙動へ戻す修正だけなら要件書の不要な変更を避ける。ユーザー向けの意味を変える場合のみ要件書も更新する。

## Constraints

- ユーザーの現時点の依頼は調査・改善案の具体化まで。コードを変更しない。
- macOS、SwiftUI、限定的AppKit、公開AX API、既存Sessionへの集約を維持する。新規依存や保存モデル変更を前提にしない。
- AX呼出はメインスレッドをブロックさせない。キャンセル要求と実行中AX呼出の停止を同一視しない。
- 失敗で登録を黙って解除しない。候補から消えたウィンドウや利用不能な登録も復旧可能性を保持する。
- 実機で最小化可能な窓だけが保証対象。列挙漏れ・権限・アプリ応答失敗は診断可能にし、成功扱いしない。

## Verification Candidates

1. 自動最小化ON、登録窓はキャッシュで全解決、サービス一覧には追加の未登録窓がある場合に、その窓へ最小化を試みる。
2. 切替中に取得済みの十分な候補を再利用し、不要な全列挙を重複しない。自動最小化OFFの既存高速経路も維持する。
3. fakeのAX操作を制御し、Aの最小化中にB→Cへ切り替えても、最終的にC向け処理が実行される。
4. 手動最小化中の切替でも要求を失わず、旧完了で新処理のbusy状態を解除しない。
5. 旧処理による既実行の副作用を記録しつつ、古い登録集合で復元を続行しない。
6. 単一窓のAX失敗が他窓の処理を妨げず、失敗・保護・中断を区別できる。
7. 同じ登録集合・候補集合に対する主画面・Status Item・Launcherの結果を揃える。
8. Terminal、同名・同位置の別窓、空Boardの現行方針を明示して回帰を防ぐ。変更する場合は先に要件を合意する。

ビルド成功、fakeテスト成功、実機のAX操作成功は分けて報告する。このDiscoveryではビルド・テスト・実機再現を実施していない。

## Viability Check

採用後に別エージェントが現行コードを読み取り確認した。案Bに静的確認上の実現阻害要因は見つからなかった。新規依存を追加しないため、追加ライブラリの保守・ライセンス評価は不要。実行中の同期AX呼出を強制中断できないこと、候補キャッシュに網羅性のメタデータがないこと、手動・自動処理の共通完了境界が必要なことを確認し、上記方針に反映した。実機での成立や性能は未検証。
